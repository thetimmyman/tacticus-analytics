# Android runtime proposal

Status: provisional native candidate. Physical Android release qualification and full feature parity remain open. This proposal does not select a permanently locked mobile stack.

Android and iOS share a secret-free document boundary, integer calculations and migration/identity semantics. Platform UI, vault, lifecycle and system document pickers remain native. Android uses Java 17 native Views, system SQLite with transactions and WAL, and Android Keystore AES-GCM. There is no Electron, Next.js, PostgreSQL daemon, WebView, JavaScript bridge or hosted login in this app.

| Candidate                                        | Local storage / domain reuse                                                                          | Evidence and unresolved cost                                                                                                                                  |
| ------------------------------------------------ | ----------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Native Views + Java + system SQLite              | SQL transactions; versioned JSON projections; portable domain behavior expressed with strict fixtures | Installed prototype measured below. Minimal dependency surface; native screen parity still requires implementation.                                           |
| Kotlin + Compose + SQLite                        | Same storage semantics; shared Kotlin/Java domain possible                                            | Credible native alternative, not built or benchmarked here. Adds compiler/UI dependencies; no demonstrated parity benefit yet.                                |
| Bundled mobile web + native SQLite/vault adapter | Reuse parts of the web UI, with platform storage/security adapters                                    | Credible alternative, not built or benchmarked here. Existing hosted service/database assumptions require a port; a bridge increases the credential boundary. |

The installed synthetic prototype wrote and read SQLite, calculated raid damage, exported/imported data and reopened after process force-stop while airplane mode was enabled. API 35 x86_64 emulator: 51 checks passed in 860 ms; 6 reopen checks passed in 21 ms; cold native Activity launch took 607 ms. The development APK was 56,112 bytes, SHA-256 `6be20b303697be86042b584905b6c3e8da396de254a9ee93c843f686bad65d56`. These are single-run prototype observations, not framework comparisons or performance guarantees. The implementation and reproducible measurement runner follow in this draft; qualification must bind a committed source and artifact digest. Emulator evidence is not physical-device evidence.

[Android Keystore](https://developer.android.com/privacy-and-security/keystore) keeps the encryption key in the platform key store. Credential ciphertext stays in the app's no-backup directory; private SQLite contains capability references, never credential values. [Backup exclusions](https://developer.android.com/privacy-and-security/risks/backup-best-practices) are explicit. No root, cross-app private storage, broad storage permission or direct game-client scraping is supported.

The Player response has metadata scopes, update time and optional key expiry, but no stable Player ID. Player scope and explicit observed-name confirmation are mandatory for new personal content. Display-name equality is a conservative anti-mixing check, not identity proof. Guild and Guild Raid are optional and can share one vault reference or use separate references. Raid responses lack a guild ID; the same key must successfully read Guild to bind Raid independently. Previously synced data remains readable after expiry, refusal, disconnect or failed refresh. Imported content is historical and cannot import verified authority.

Cloud contribution remains default-off and unavailable without a reviewed authority/transport adapter. Scheduled official reads are separately opt-in, constrained by charging/idle/unmetered network and never enable cloud contribution. Revocation advances local generations and purges queued rows. Onboarding does not imply contribution consent. Android addon access is builtin-vetted-only; user-selected authorized documents are the supported fallback for content unavailable from official scopes. No official Guild War or Replay source is asserted.

Before a full-port decision is qualified, test the lowest supported API, phone/tablet layouts, actual physical release builds, lifecycle/battery behavior, protected owner signing and every accepted feature row. Native storage compatibility is an implemented first slice; the existing web feature inventory remains acceptance work.

Android authorization uses the OS user/profile's current secure, unlocked device state through [KeyguardManager](https://developer.android.com/reference/android/app/KeyguardManager). Credential operations and document import/export recheck that state; the foreground requests a single OS unlock only when needed. No workspace password or portable session token is collected or cached. Background reads hold when locked. Workspace scope ownership is separately bound by native SQLite references and connection generations. This is a native device-session adapter, not the desktop signed local-Auth token protocol. Devices without a secure screen lock hold sensitive operations.

API 35 additionally requires the Keystore key to be used on an unlocked device. [The platform documents bugs on older versions](<https://developer.android.com/reference/android/security/keystore/KeyGenParameterSpec.Builder#setUnlockedDeviceRequired(boolean)>), so API 26–34 use explicit native checks and remain unqualified for hardware lock behavior until physical testing. Removing screen-lock credentials, vault loss and OS-specific recovery retain offline data and require re-entering official keys; no backup contains credentials. The emulator runner uses a fixed synthetic PIN solely to measure actual locked access refusal and offline-data retention.
