# Native mobile architecture candidate

The Android and iOS implementations agree a native UI, a private SQLite projection store and the platform vault as the first candidate to measure. iOS uses UIKit/Swift and system SQLite; Android evaluates native Views and SQLite with Keystore. The shared boundary is secret-free versioned documents, integer analytics, scope verification semantics and consent generations. UI, secure input, vault operations, scoped file selection, lifecycle and packaging remain platform-native. There is no downloaded executable addon or arbitrary native request bridge.

| Candidate                     | Benefit                                                              | Cost and unresolved evidence                                                                                           |
| ----------------------------- | -------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| UIKit, Swift, system SQLite   | Bundled OS services, native accessibility, no web or backend runtime | Existing application features require explicit native projections and parity work                                      |
| SwiftUI, system SQLite        | Native declarative UI                                                | Deployment-version and lifecycle behavior need separate measurements; chosen UI candidate is UIKit                     |
| WKWebView with bundled web UI | Potential reuse of interface components                              | Requires a complete local API and privilege bridge; existing server/database assumptions do not transfer automatically |
| Desktop runtime/sidecars      | Existing desktop implementation                                      | Persistent Electron/Next/PostgreSQL processes are not a supported iOS application composition                          |

The first measured vertical slice will build and install an actual Simulator app, create a protected local SQLite database, write/import synthetic rows, calculate integer damage per token, terminate and relaunch, and confirm persistence. Hosted tests measure build artifact bytes, launch and storage/calculation timing and record the actual Xcode/SDK/OS/architecture. These measurements select a mobile implementation candidate; they do not establish full canonical SQL parity, performance budgets or a physical-device release pass.

Keychain uses foreground-only, device-only accessibility and no synchronization. Apple documents that [device-only Keychain items do not migrate to another device](https://developer.apple.com/documentation/security/ksecattraccessiblewhenunlockedthisdeviceonly). Local files use iOS Data Protection and are excluded from automatic device backup; explicit exports contain approved local data only. Restoring exported data requires reconnecting official read credentials. Physical lock-state, file protection, key migration and backup behavior require device evidence; Simulator results are separate.

The deployment target begins at iOS 17 as a candidate, not a proven support minimum. The hosted workflow records the actual available Simulator runtime. [GitHub's macOS image inventory](https://github.com/actions/runner-images/blob/main/images/macos/macos-15-Readme.md) identifies available Xcode and Simulator inputs; the build checks and records selected versions rather than treating a runner label as evidence.

New ordinary workspaces request Player, Guild and Guild Raid. Verified Player data and explicit display-name confirmation are required before enabling personal content. Optional scopes may be skipped. Player responses do not establish stable account ownership; Guild Raid responses do not establish a guild identity. Same-key Guild access is required before a Raid scope is bound. Official keys use secure native input and Keychain; local game-client secret discovery is safely unavailable.

Full feature, SQL/function/policy, asset-rights and security acceptance stays open. A mobile projection store is not an assertion that every production migration or analytics feature has parity. The capability matrix must retain those gaps until their actual native behavior is implemented and tested.
