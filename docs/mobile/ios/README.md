# Native iOS workspace

The app uses UIKit and Swift, the system SQLite library, and foreground Keychain access. There is no web runtime, bundled database service, shell bridge, downloaded executable extension, or production contribution sender. The deployment target is iOS 17; support on that minimum version still requires testing.

Open `apps/mobile/ios/TacticusIOS.xcodeproj` and select the shared `TacticusIOS` scheme. The checked-in project is generated by `python3 apps/mobile/ios/scripts/generate-project.py` without external project tooling. The programmatic interface supports phone and tablet layouts, Dynamic Type and native accessibility controls.

The new personal workspace requires an independently successful Player read and explicit display confirmation. Every connection requests Player when required, plus optional Guild and Guild Raid. A combined key uses one Keychain reference. Optional keys may use separate references. Guild Raid is held unless Guild is observable on that same key. Upstream Player does not supply stable account identity; display confirmation is never an ownership claim. Previous projections and local calculations stay readable when a refresh is unavailable, expired, skipped or disconnected.

The native secure field clears after submission or cancellation. Requests go only to the fixed official HTTPS endpoints; redirects, cookies and response caching are disabled, and response size/time are bounded. Keychain items are non-synchronizing, `WhenUnlockedThisDeviceOnly`. SQLite files use complete file protection and are excluded from automatic backup. The background privacy veil closes SQLite and cancels foreground requests. This is implementation evidence; Simulator Keychain checks do not prove physical lock-state protection.

The workspace retains the complete allowlisted official Player projection, including inventory, campaigns, legendary-event progress and detailed roster fields. The bundled projection rules are byte-for-byte checked against the shared canonical schema. Native drilldown views page arrays and object fields in groups of 50. The portable core still contains the Player display, roster identifiers/names/ranks/levels and raid/bomb resource projections. Local user-supplied raid rows use exact integer totals and floor damage per token. A newly created personal workspace cannot add rows before Player verification. The Simulator-only synthetic demo has a separate database and a visible mode label. Imported documents become unverified historical data and clear capability references, consent and queues.

Import and export use the native document picker with an explicitly selected file. The strict, bounded `mobile-workspace/v1` core excludes credentials, opaque Keychain references, raw API responses, verification claims, preferences and queues. A separately versioned `ios-local-backup/v1` envelope includes the core document and a strict `official-player-cache/v1` projection. Full backups are limited to 6 MiB, cached Player data to 4 MiB; foreign or inconsistent Player/core pairings, unknown fields and future versions are refused before replacement. Both formats restore unverified history and remove scope references, sharing consent and queues. Backups contain no Keychain material or authority. Full guild/raid payloads, legacy application history and cross-platform full-archive interchange remain implementation gaps. SQLite v1 to v2 adds the protected Player cache in a transaction; failed migration retries preserve the existing core, capabilities and preferences. Combined Player/core writes and document replacement are transactional; future database versions are rejected without migration. A storage page budget supports a real SQLite-full rollback check.

Meta and Portal each have independent Raid, War and Replay preferences, off by default. Changes advance the local generation and purge that purpose/dataset queue. Only Raid can be staged locally; War/Replay staging and all cloud sending remain unavailable pending their reviewed domain payloads, binding, envelope and transport. Core reading and calculations do not require sharing.

The hosted workflow runs XCTest on freshly created phone and tablet Simulators, then builds the Release configuration. The retained app zip is the Debug app actually installed by the tests, bound to its digest in `platform-evidence/v1`. Synthetic onboarding tests use an explicit source and vault double; a separate test performs real Simulator Keychain CRUD. Installed UI tests exercise cached inventory pagination, progress inspection after process restart, background dismissal, offline save, exact calculation display, process relaunch, background/foreground, mandatory Player holding and the native secure field. Raw diagnostic logs and Simulator inventory are not uploaded.

Run the owned proof script only on disposable Xcode capacity:

```sh
python3 apps/mobile/ios/scripts/simulator-proof.py \
  --output /absolute/new/disposable/output \
  --sha FULL_PUBLIC_SOURCE_SHA
```

No signing identity is created by the project or workflow. Simulator apps are not physical release artifacts. Owner-provided provisioning/signing and physical iPhone/iPad installs remain required, along with minimum-version testing, device lock/backup checks, real airplane and suspend behavior, thermal/storage interruption, upgrade/rollback/uninstall, authorized live onboarding, reviewed shared-data addons, contribution integration, canonical database-history equivalence and the full existing feature inventory. The current native slice does not close those acceptance gates.
