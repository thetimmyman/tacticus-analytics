# Windows qualification candidate

The candidate adapts the existing Electron, Next standalone, PostgreSQL, Supabase Auth and PostgREST application to Windows x64. It preserves the existing local schema and synthetic graphical journey. It does not establish full application parity or authorize a public release.

The intended consumer target is Windows 11 x64. The workflow exercises Windows Server on standard GitHub-hosted capacity. That evidence cannot establish ordinary standard-user installation, UAC prompts, SmartScreen, antivirus behavior or a consumer Windows host. Other Windows versions and architectures remain unqualified.

## Native ownership and storage

`TacticusDesktop.exe` creates a private Job Object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`. It creates the bundled Node process suspended, assigns it before resuming, and terminates it if assignment fails. The job handle is never inherited. Node owns the existing real service and Electron processes; closing or killing their native owner closes the job. The native proof exercises a child and grandchild on normal job close and forced owner death.

The owner rejects reparse paths, applies a protected current-user/SYSTEM ACL to workspace and installation roots, and holds an exclusive OS file handle to prevent concurrent workspace launch. An abandoned process releases this handle without stale PID guessing. PostgreSQL, Auth, REST and the application bind only loopback and choose separate ports. A competing port causes startup failure, rather than binding a public interface. No firewall rule is installed.

An invocation with an enabled Administrators or Power Users group starts the runtime with a restricted version of the same user's primary token. Those groups become deny-only and administrative privileges are removed; the user SID, profile, environment and private workspace ACL remain the same. Standard-user invocation keeps its ordinary token. A failed reduction refuses startup without an administrative fallback. The child starts on the owner's existing window station and thread desktop, whose names are read from borrowed OS handles and supplied explicitly during token reduction. This does not change desktop ACLs, discover other desktops or grant additional access; an inaccessible desktop still refuses startup. The child still starts suspended, joins the private kill-on-close Job Object and resumes in the foreground. The native proof checks the retained user and disabled privileged groups, compares the actual child desktop with its parent and tests descendant cleanup under that token. [PostgreSQL's Windows startup check](https://github.com/postgres/postgres/blob/REL_18_6/src/backend/main/main.c) refuses enabled administrative groups; [CreateRestrictedToken](https://learn.microsoft.com/en-us/windows/win32/api/securitybaseapi/nf-securitybaseapi-createrestrictedtoken) provides the same-user reduction without changing UAC or account policy. Hosted execution does not replace consumer standard-user qualification.

The pinned PostgreSQL binary fails initialization under a Unicode binary path because it emits that Windows ANSI pathname into UTF8 SQL. The native owner requests an ASCII short-name alias only for the verified bundled PostgreSQL directory and verifies that its expanded name matches the original directory. The actual installation and workspace retain their long Unicode paths. This is a constrained compatibility adapter, not complete Unicode-path support: a volume without an ASCII alias refuses database activation and remains unqualified. No filesystem policy or database encoding is changed. The [upstream path-encoding diagnosis](https://www.postgresql.org/message-id/2932627.1615761527@sss.pgh.pa.us) and [Windows short-name API behavior](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getshortpathnamew) explain this remaining gate.

Official API input uses Windows CredUI and Credential Manager. The fixed operations are prompt/store, read Player/Guild/Guild Raid from `https://api.tacticusgame.com`, confirm displayed Player and delete a known opaque reference. There is no arbitrary URL, credential enumeration or game-client protocol. Keys never enter renderer input, workspace JSON, backups, diagnostics or Node IPC. Response size, redirects and key echoes are rejected in the native process. Windows vault failures fail closed; there is no plaintext fallback. Managed HTTP header strings cannot be guaranteed erased immediately; native buffers and mutable byte arrays are cleared.

The exact reviewed workspace onboarding v1 guard runs in the device supervisor. Native calls return opaque references and bounded responses; the guard returns projected roster/resources and capability/freshness state. Player validation and user confirmation are required for a new personal experience. Optional scopes can be absent. Offline reopen uses retained projections. This upstream API provides a Player display name rather than independent account ownership proof, and Raid requires same-key Guild access for guild binding. Contribution enrollment requires separate consent. Applying official projections throughout all existing application pages is still an integration gate. The separate demo route contains synthetic data and is not a personal account. Legacy hosted credential forms and their key handlers receive a native-input holding response even after activation/import, covering profile/onboarding/roster, token usage and guild settings/members. Those accepted features remain unqualified until their native adapters are integrated; this protection is not an approved feature exclusion.

The workspace opens automatically under the logged-in Windows account. Electron main obtains an expiring owner Auth session from a separate fixed-endpoint partition using a private bootstrap capability. The normal renderer receives Auth session cookies; the bootstrap capability never enters its headers or cookies. Fresh, interrupted and former password accounts keep their stable owner; a random ephemeral Auth credential stays in memory and is replaced on reopening. There is no workspace password, password-change, recovery-code or logout flow. The supervisor requests the current session through inherited IPC and can renew it through main. Local Auth `/user` verifies the owner before credential access and projection reads/writes; every native access and synchronous commit also rechecks the HS256 signature, owner and expiry. Expiry during file choice refuses access; one bounded retry uses a renewed native session and retains only the selected path inside the supervisor. Native vault recovery journals opaque targets and removes only authenticated unused entries, preserving committed references after interruption. The installed qualification includes a separate former password synthetic database fixture and cached local restart; real migrated API vault bindings remain a qualification gate.

Local PostgreSQL/Auth/REST service material is stored in a distinct Credential Manager target and read only by the supervisor. Temporary initialization/SQL files live under the protected workspace and are deleted after use. Native helper failures retain only a numeric exit status and fixed category from a bounded in-memory diagnostic prefix; helper output never enters diagnostic text. The native proof separately initializes and reopens synthetic service material under the same-user reduced token, removes its unique target and records only a success assertion. Service output is drained without recording bodies; transport configuration reaches Electron over stdin rather than an ordinary JSON file.

## Build and installation

Development builds require Node 22, .NET SDK 10.0.401 and Go 1.27.0. They are build inputs, not end-user prerequisites. The published native host includes the .NET runtime in a single executable. Runtime staging bundles Node 22.23.2, Electron 44.5.1, PostgreSQL 18.6, PostgREST 16.4 and Auth 2.197.0. Archive digests and the exact Auth source commit are pinned in `build-runtime.ps1`; Auth has no upstream Windows release binary and must successfully build from that source. Go module verification runs before compiling it. Staging retains PostgreSQL server/tools/extensions/resources while excluding separate administration products. PostgREST's actual libpq dependency closure is copied beside it. The full locked Windows Sharp package, including its adjacent libvips DLLs and licenses, is retained because Next file tracing omits those DLLs. Microsoft Visual C++ application-local runtime DLLs come from the licensed build-tool redistributable directory, require a valid Microsoft publisher signature and have exact digests in the bundle inventory. A bounded PE import audit refuses unresolved third-party DLLs for the executed baseline closure. Optional extension dependency and redistribution/complete-notices review remain gates. [Microsoft redistribution guidance](https://learn.microsoft.com/en-us/cpp/windows/redistributing-visual-cpp-files?view=msvc-170) permits app-local DLL placement subject to the applicable Visual Studio license and distributable-code terms; hosted preinstalled runtimes are not accepted as bundled dependencies.

The unmodified Auth release fails Windows compilation because its HTTP listener unconditionally calls Unix `SO_REUSEPORT`. The small owned `auth-windows.patch` adapts only that source copy to Windows `SO_EXCLUSIVEADDRUSE`, retaining the service and migrations and avoiding Windows address reuse. The derived version is labeled `2.197.0+windows.1`; it is not an upstream Windows release. [Microsoft socket options](https://learn.microsoft.com/en-us/windows/win32/winsock/using-so-reuseaddr-and-so-exclusiveaddruse) explain the exclusive binding choice.

```powershell
npm ci --no-audit --no-fund
$env:STANDALONE_BUILD = 'true'
npm run build
./apps/desktop/platform/windows/build-runtime.ps1 -Output "$env:TEMP/Tacticus candidate"
& "$env:TEMP/Tacticus candidate/TacticusDesktop.exe" setup-candidate "$env:TEMP/Tacticus candidate"
```

The native setup prompts before installing into the user's Programs directory, creates a Start menu shortcut and an HKCU uninstall entry, and requests `asInvoker` privileges. It stages exact inventoried files into a new version directory, verifies sizes/digests while reading the same locked file handles, and atomically changes the active pointer only after verification. A failed update leaves the previous pointer intact. The `rollback` operation verifies the previous version before activating it. Schema hash mismatch refuses startup without replacing existing data; arbitrary migrations are not accepted. A transactional schema upgrade with full canonical parity remains a gate.

Uninstall retains the workspace and vault references for reinstall. A temporary single-file helper waits for the installed process to exit before deleting its installation. Its small temporary executable remains for later maintenance; complete cleanup and locked-file recovery require consumer qualification. Workspace deletion is not offered by this candidate.

`install` deliberately refuses production installation because no owner-approved signing identity or signed release trust policy is enrolled. Candidate SHA-256 verification detects substitution against its supplied inventory, and is not publisher authentication. Signed manifest integration, Authenticode verification and malicious signed release qualification are required for production promotion.

## Qualification and remaining acceptance

The workflow builds the native host and runs the adversarial native proof. A separate job builds the complete application, stages the real Windows components, installs the candidate under a space/non-ASCII path and performs the existing graphical synthetic first-launch/restart journey through the installed artifact. Evidence includes actual PR head source commit, manifest digest, package bytes, timings and Windows Job Object peak committed memory (not RSS) and explicit candidate/standard-user flags. Failed builds or journeys are failures, not parity evidence.

A separate helper diagnostic starts the exact bundled Node binary under the same reduced owner token, desktop and private Job Object. It compares hidden pipes, attached pipes and hidden launches with inherited input, invoking only synthetic service-material and desktop helpers. Its receipt contains numeric status and fixed operation/mode fields, source and native/Node digests, and explicit diagnostic-only and unqualified-application flags. Desktop names remain inside a protected temporary directory and are deleted after measurement. Successful diagnostic completion does not qualify the installed application journey.

The measured reduced-token diagnostic refuses hidden-pipe helper launches with DLL status `0xC0000142`, while attached pipes and inherited-input launches complete service-vault and desktop checks. Owned runtime children therefore retain the existing owner console connection with private input/output pipes. This avoids Node's `CREATE_NO_WINDOW` flag without detaching processes, restoring administrative privileges or changing desktop permissions. Graphical console visibility and ordinary consumer installation still require supported-host qualification.

The installed journey uses a unique directory under the current user's application-data location, matching the ordinary per-user installation volume. Staging and sanitized evidence remain in the hosted scratch directory. The actual installation and both fresh and former-password workspaces retain spaces and Unicode characters; the native owner must verify the bundled PostgreSQL alias before services start. An earlier hosted scratch-volume installation was refused because that volume supplied no ASCII alias. Moving this qualification to the user profile does not qualify volumes without aliases or change filesystem policy.

The cached-reopen scenarios use retained local data and Electron's external renderer-request filter. They do not establish OS-level external network denial for the whole process tree; evidence states that limitation explicitly. Service startup failures retain only a fixed category and numeric process status from a bounded in-memory prefix, never raw service output.

Portable adapter tests exercise the actual shared onboarding guard with synthetic upstream responses: Player-only access, missing Player, unavailable vault, combined scopes, wrong guild, revoked replacement retaining local data, disconnect and secret-free renderer views. Inventory tests reject mutable state and package links. Session tests reject forged, expired and mismatched owners; an Auth HTTP test proves credential operations are refused before ownership approval and expiry during a native prompt cannot write state. PE negative controls reject missing runtimes and corrupt import tables. These are adapter tests, not claims of native CredUI automation or live API validation.

Native common file dialogs implement projection export and historical import. Export strips vault references by taking the guard's public projection; native validation refuses credential-bearing fields and applies a current-user/SYSTEM ACL to the chosen file. Import uses a bounded same-handle read and preserves its historical/offline status rather than claiming new verified Player access. The optional-scope UI accepts separate keys or rechecks the connected Player key and provides explicit disconnect. Interactive file dialogs and secure prompts still require consumer-host testing.

Export separates destination selection from the protected write. If the session expires during file choice, only the supervisor retains that destination in memory and resumes it after automatic native session renewal. The renderer receives no destination path. Native writing uses a protected temporary file and checks the authenticated session deadline before the atomic replacement; an expired export preserves the existing destination.

Historical import similarly separates the native file choice from reading. The supervisor rechecks local authorization after file choice; the native reader checks the deadline before opening and after its bounded read, refusing devices and final reparse points. Only the supervisor keeps the selected path across an expired session. A complete field-only Player schema revalidates the snapshot, summary and timestamp before import into an empty workspace. Imported data remains historical and requires reconnection; imported capability or identity claims cannot authorize upstream reads.

The installed recovery journey exercises the real components after the synthetic graphical import: a failed SQL transaction, Auth crash stopping the stack, restart retaining canonical rows, incompatible schema rejection before services, and stopped-database checkpoint/restore under the same workspace/vault binding. PostgreSQL attempts a fast `pg_ctl` stop before termination. Fresh-install identity transfer, arbitrary backup imports and full transactional schema upgrades remain separate gates.

The full accepted feature matrix remains open. Required external or integration gates include consumer standard-user install/uninstall and signing identity; SmartScreen/antivirus and locked files; suspend/resume; native file chooser and export/backup/restore; token expiry and interrupted migrations; full local schema/extensions and application feature parity; official projection integration and progressive separate-key UI; license/redistribution and complete bundled notices; release-manifest trust and real module/broker integration. Hosted native proof cannot replace these measurements.
